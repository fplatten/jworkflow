# M5 build-first evidence register

**Status: functional checkpoint complete on Windows against a fake provider** (October 3, 2026). WB-18–WB-20 deliver the fixed-model streaming adapter, session consent, persistent conversations, `/clear` and `/cancel`, and approved, undoable block proposals.

**Live provider compatibility (G-06) is not yet proven.** All evidence below uses a local fake Responses server. No real AI request was made during M5 work. Diagnosis of build/test output (AI-05) depends on M6 and is not implemented.

## Delivered

**WB-19 — Fixed-model adapter (`ResponsesChatModel`, the single Spring AI `ChatModel`)**
- Always sends `gpt-6-astra` with `store=false`. A runtime model option is ignored, and configuring another `spring.ai.openai.chat.model` fails at startup. This closes the M1 override defect.
- `stream()` implements Responses Server-Sent Events with the JDK `HttpClient`: text and refusal deltas, then the final response with tool calls and usage. Disposing the stream cancels the HTTP exchange and interrupts any retry wait.
- Retries follow `spring.ai.retry.max-attempts` (the first try included) and `spring.ai.retry.backoff.{initial-interval,multiplier,max-interval}`. Only 429/5xx and network failures *before any streamed output* are retried, so a retry never replays output and there is no second retry loop.
- Failures are classified (authentication, model unavailable, rate limited, provider, malformed, interrupted). Messages contain only a provider error code, never the key or provider text.
- The key is read from the runtime environment (`OPENAI_API_KEY` via `spring.ai.openai.api-key`) on each request. Startup never contacts the provider. Without a key, the assistant reports itself unavailable and manual authoring is unaffected.

**WB-18 — Consent, history and lifecycle (`AssistantService`, `ConversationStore`)**
- **Shareable files:** a session-scoped list of files the user can share.
  - Never offered: `.git`, `.jworkflow`, build/IDE/dependency folders, binaries, files over 64 KiB, and non-UTF-8 files.
  - Hidden as secrets: `.env*`, key/certificate stores, names containing secret/password/token, and files whose content looks like a private key or API token.
  - Gitignored files are also hidden (a conservative subset: a match always hides).
- **Workflow sharing:** sharing the current workflow and discovered command names is a separate checkbox.
- **Revocation:** unchecking a file removes it. A project change or restart clears all sharing, and resuming a conversation never restores it.
- **Data, not instructions:** shared content is sent inside `<project-data>` with an instruction that it is untrusted data. The system prompt states that such data cannot grant access, approve or change the rules. The assistant has exactly one tool and cannot read files or run anything.
- **Conversations:**
  - Stored as `.jworkflow/conversations/<uuid>.json` and kept until the user deletes them; there is no pruning.
  - A new conversation starts when a project is confirmed. Saved conversations can be resumed explicitly, and deletion asks for confirmation.
  - History sent as context is bounded to about 40,000 characters; trimming never deletes saved history.
  - Transient messages are never written. This flag is reserved for M6 diagnostic excerpts.
- **`/clear`:** deletes the current conversation immediately. It is refused while a request is active ("Use /cancel first"). It is never queued, and other conversations and the workflow are untouched.
- **`/cancel` during AI:** stops the stream, closing the provider connection, deletes the current conversation, starts a new one and discards pending proposals. A generation counter and a deleted-ID tombstone suppress late output and late saves. Idle `/cancel` reports "No active operation."
- **Deadline:** a 10-minute overall limit (`workbench.ai.deadline`) includes retries, backoff and streaming; output does not extend it. On timeout the partial reply is kept and marked `incomplete`.
- **One request at a time:** a single active AI request; other input is rejected as busy, never queued.

**WB-20 — Approved block proposals (`WorkflowEditProposals`)**
- **The only tool:** `propose_workflow_edit`, carrying a summary and 1–20 operations (`add_node`, `set_field`, `remove_node`, `set_start`).
- **Strict validation:** field names per block type, operator and value-type enums, length and control-character limits, unknown properties rejected, and references checked against the shared workflow.
  - Step actions must be discovered commands; the assistant cannot invent actions.
  - Any invalid part rejects the whole proposal with "Nothing was changed".
- **Review in the browser:** the proposal shows its summary and a semantic preview (for example "Add end 'archived' after 'done'"). Approval:
  1. checks the editor still matches the state the request was based on (SHA-256 of the editor state)
  2. re-checks that every referenced node still exists
  3. claims the proposal once on the server; cancel or clear invalidates it
  4. applies all operations as **one Blockly event group**, so one Undo restores the previous IDs, connections, values and layout
- **After applying:** the draft is unsaved and dirty. Nothing is saved or generated automatically, and source changes still require Generate and the M4 diff review.

**Terminal**
- Streamed deltas render as sanitized plain text, so control characters cannot inject terminal escapes.
- `/help` lists `/clear` and explains that any other text goes to the assistant.
