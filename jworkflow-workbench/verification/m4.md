## Design: how generated sources meet the pinned core

These facts come from reading the core (`InMemoryWorkflowEngine`, `WorkflowEngineBuilder`, `GroovyWorkflowDslCompiler`, `jworkflow-example`) and are proven by tests:

- A Groovy step's `action` runs through `WorkflowEngineBuilder.stepHandler(action, handler)`. The handler's `StepResult` drives the generated `onSuccess`/`onFailure` routes.
- A step runs when its instance receives an event or signal, and **each sequential step needs its own signal**. The end-to-end test needed exactly 2 signals for 2 steps.
- Core has no command bus. `org.jworkflow.application.Command` is a marker interface, and the example wires listener → command → user dispatcher → service.

Generated artifacts per enabled step action:

| Artifact | When | Shape |
| --- | --- | --- |
| Workflow Groovy | Always | `<output>/<engineId>.groovy` from the M3 emitter. |
| Command | Only if the action names no discovered command | `public record X(String businessKey, Map<String, Object> variables) implements Command` in the confirmed package. Generate reports `COMMAND_WILL_BE_CREATED` as a warning (INT-01: a missing command prompts creation). Invalid class names remain the blocking error `ACTION_UNKNOWN`. |
| Listener | Always, unless mapping is ambiguous or the file is user-owned | `XListener implements StepHandler` in the command's package. It builds the command from the step context and calls a user-supplied `Consumer<? super X>`. A runtime exception becomes `StepResult.failure`, so the failure route is taken. |

The listener has no Spring annotations and no generated dispatcher or service (INT-01). Record components are mapped by name:
- `String businessKey` comes from the instance business key.
- `Map<String, Object> variables` gets all variables.
- Numeric primitives use `Number` conversion and `boolean` uses `Boolean`.
- Other types are cast, with `@SuppressWarnings("unchecked")` only for generic types.
- `char`, malformed types and non-record commands are ambiguous. In those cases the listener is not generated and the plan says what to write.

**Ownership:** Workbench updates a generated file only while its hash still equals what Workbench last applied (`.jworkflow/applied.json`). User-written or user-edited listeners are kept unchanged and listed as discrepancies. User commands are never modified.

## Delivered behavior

- **Proposal (`POST /api/project/changes`).** It is bound to the saved, successfully generated revision. It contains every file's full unified diff, before/after SHA-256 hashes, the base revision and document hash, and the profile, package and discovery assumptions. It also lists artifact statuses and discrepancies. The schema is `schemas/source-change-proposal-v1.schema.json`.
- **Approval (`POST /api/project/changes/apply`).**
  - It covers the whole set; there is no per-file or per-hunk choice.
  - The server recomputes the proposal and rejects any token difference. A changed file, revision, package or discovery state therefore invalidates approval.
  - Editing in the browser after review hides the proposal and marks it **Stale**. Reject writes nothing.
  - A manually edited Groovy file needs an explicit "replace" confirmation in addition to approval.
  - Repeat apply returns `already-applied` without writing.
- **Journaled apply (`ChangeSetStore`).**
  - Before/after copies are staged in `.jworkflow/journal/` and each file is written by temp-file and atomic move.
  - Any I/O or runtime failure rolls every file back, so a partial set is never reported as success.
  - A process death leaves the journal. The next project confirmation rolls back, or finishes a committed set. If a file changed meanwhile, the journal is kept and further writes are blocked with a message naming the file.
- **Revert.** Only the latest successfully applied set is kept, in `.jworkflow/backup/`, and it is replaced after the next success.
  - The reverse diff needs its own approval and is refused when any file changed after apply. Created files are deleted and updated files restored.
  - Obsolete files from older changes are never touched.
  - After a revert, no revert point remains.
- **Integration plan (`.jworkflow/integration-plan.md`).**
  - **When written:** on every Generate and after apply or revert; shown in the browser.
  - **Status table:** workflow, version and revision, whether static validation passed, whether changes are proposed only, applied for this revision, or applied for an older revision, and "Build and tests: not run".
  - **Body:** problems, artifacts, per-action payload mapping, a `WorkflowEngine.builder()` wiring snippet with `stepHandler(...)` lines, triggering guidance, the dependency, Java target and resource-loading setup, and discrepancies.
  - **Discrepancies include renames and obsolete files:** an old engine ID and previously applied files that are no longer part of the workflow are listed for manual cleanup, never deleted.
  - **What it never contains:** build or test transcripts.
- **Discovery fix.** Record components are now split only on top-level commas and annotations are stripped, so `Map<String, Object> variables` and `@Deprecated BigDecimal amount` are discovered correctly.

## Known limitations and deferred work

- **Existing user-written Java is never edited.** WB-14 allows reviewed source-preserving updates to existing listeners and commands. This checkpoint takes the conservative path (keep the file and explain) because a safe Java rewrite needs a real parser. Owner decision: keep this behavior, or schedule a parser-based editor.
- **Events are not generated.** Steps are driven by signals or events the user delivers, and the plan explains how. No event records are created because no block declares one.
- **Limited applied-record history.** The applied record keeps one previous level, so after two renames only the most recent old name is listed.
- **Case-collision rejection (SEC-01) is still missing.** Paths come from validated identifiers and the confirmed package.
- **Not done yet:**
  - M6: `/build` and `/test` locking of apply and revert
  - M7: permission and disk-full tests on real filesystems, scale, and coverage (branch coverage is still below 80%)
- **macOS:** not run.
