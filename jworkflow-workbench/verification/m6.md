# M6 build-first evidence register

**Status: functional checkpoint complete on Windows for Maven** (October 3, 2026). **Owner decision:** on Windows, `/build` and `/test` are Maven-only for the MVP. WB-21–WB-23 deliver:
- OS-enforced confinement with a per-machine self-test
- controlled `/build` and `/test`
- one operation slot with source locks
- the final terminal state machine

**Open:**
- **Gradle on Windows is out of MVP scope** (owner decision, see Scope decision).
- **macOS confinement is implemented but has never run.** It stays disabled on a Mac until its self-test passes there.

## Delivered

**WB-21 — Confinement (`Sandbox`, `WindowsAppContainerSandbox`, `MacSandbox`, `SandboxProbe`, `SandboxSelfTest`)**

Windows:
- **Isolation:** each launch runs in a capability-less AppContainer, so the network is isolated and file access is limited to explicitly granted folders.
- **Process tree:** the process starts suspended in a kill-on-close Job Object, and only the output pipe and NUL input are inherited.
- **Folder access:** Workbench grants the container modify access to the project folder only, after the user approves it. Read-only tool and cache folders are never changed by Workbench; the self-test prints the exact `icacls` commands for the user to run.
- **Drive letters:** each launch maps the project and every read-only folder to a free drive letter (`DefineDosDevice`, the API `subst` uses) and removes the mapping afterwards. Inside an AppContainer, `Path.toRealPath` must list every ancestor folder, and `C:\` never allows that; Maven needs it for its working directory and javac for the JDK. Mappings left behind by a crash are cleared at the next launch.
- **Environment:**
  - **Allowlisted variables only**, so no API keys or tokens reach the build.
  - **`SystemRoot` is always kept,** whatever its case; Winsock fails without it.
  - **`LOCALAPPDATA` is always supplied,** because AppContainer process creation fails without it.

macOS:
- `sandbox-exec` with a deny-by-default profile: reads limited to the system, the read-only paths and the project; writes only in the project; network denied; process execution limited to those paths; Mach lookups limited to a short list.
- A `perl setpgrp` process group whose whole group is killed. File metadata outside the project stays visible.

**Self-test** (run before any build, per project and session). The probe runs inside the sandbox with exactly the build's read-only paths and environment. Execution is enabled only if:
- reading and writing an outside sentinel fail
- the project is writable
- each read-only path is readable but not writable
- no secret appears in the environment
- a detached descendant does not survive
- on Windows, sockets work
- a loopback server outside the sandbox cannot be reached
- connecting to the reserved TEST-NET address `192.0.2.1` is refused by policy (`Permission denied`), so no real host is contacted

**Correction:** an earlier run reported network denial that was really a Winsock start-up failure caused by a missing `SystemRoot`. Network results are now classified, so that failure mode counts as a failure. A **negative control** runs the same probe unconfined and must fail: outside read allowed, cache write allowed, outside loopback connected.

**WB-22 — `/build` and `/test` (`BuildTools`, `CommandService`)**

The tool comes from the project wrapper (only if its distribution is already cached) or from PATH. It is launched directly through `java`, never a shell or project script. Everything runs offline and nothing is downloaded.
- **Maven** (3.9 or later):
  - **Commands:** `--offline --batch-mode`; `/build` runs `-Dmaven.test.skip=true package`, and `/test` runs `verify` with no filters.
  - **Repositories and settings:** the project-local repository is `.jworkflow/m2/repository` and `~/.m2/repository` is used read-only (`maven.repo.local.tail`). An empty settings file replaces the user's `settings.xml`, which may contain credentials. `.mvn/jvm.config` is honored.
- **Gradle:** `--offline --no-daemon`; `/build` runs `assemble` and `/test` runs `check`, with a project-local `GRADLE_USER_HOME` and the user's caches as `GRADLE_RO_DEP_CACHE`.
- **Approval and running:**
  - Every execution needs approval of the exact command, working directory, environment, read-only paths and deadline. An approval works once, and is refused if the tools, configuration or confinement changed.
  - Denying a command runs nothing; there is no automatic retry or automatic run after apply.
  - The 10-minute deadline starts at launch.
- **Output and outcome:**
  - Output streams to the terminal and is kept in a 1 MiB in-memory buffer, with visible truncation.
  - Only the outcome and a source fingerprint are saved (`.jworkflow/verification.json`), never output. The plan shows the last outcome and whether it still describes the current sources.
- **Missing prerequisites** (Maven below 3.9, or an uncached wrapper) give numbered steps for the user to run outside Workbench.

**WB-23 — Locks and state machine (`OperationCoordinator`, `TerminalSocket`)**
- **One operation at a time:** AI, build or test. Anything else is rejected as busy, never queued, and only the ticket holder can release the slot.
- **Source locks:** source apply and revert are refused while a build or test runs; editing and Save stay available.
- **Terminal commands while a build or test runs:**
  - AI input: rejected.
  - `/cancel`: stops only the process tree; the conversation and sources are untouched.
  - `/clear`: allowed.
  - `/exit`: stops the tree, then shuts down.
- **Terminal commands during an AI request:**
  - `/cancel` and `/clear` keep their M5 behavior.
  - `/exit` abandons the request without deleting history.
- **Shutdown:** closing the owner tab shuts down the app, which kills any running tree.

## Blockers and open items

- **Scope decision: Gradle on Windows.** The owner accepted Maven-only `/build` and `/test` on Windows for the MVP. `CommandService` refuses Gradle projects on Windows before any self-test or launch (`CommandServiceTests.windowsMvpSupportsMavenOnly`, `LiveConfinedBuildIT`).
  Background: On JDK 20+, `java.io.File.createTempFile` reads volume information for the folder's drive (`GetVolumeInformation`). Inside an AppContainer that fails: `C:\` cannot be opened by app containers, and a mapped drive returns error 144. Gradle calls it at startup, so it cannot start. Gradle projects remain fully supported for authoring, generation and integration on Windows; users run their Gradle build outside Workbench.
- **Maven caveat.** Maven plugins that call `java.io.File.createTempFile` on JDK 20+ would fail the same way. The tested lifecycle (compiler, resources, jar, surefire, failsafe) does not. The self-test reports `javaTempFiles` so this is visible.
- **Real user folders not yet granted.** The real Maven proof used Workbench-owned copies. On a real project, the user runs the printed `icacls` read-only grants for their Maven distribution and `~/.m2/repository`; the self-test then confirms them.
- **macOS: not run.** `macSandboxDeniesEveryEscapeAndKillsDescendants` runs on macOS runners and machines. Gradle on macOS is likely to fail because the profile denies all networking (Gradle uses loopback to its workers); needs a run there.
- **Network evidence scope.** The checks use a loopback server outside the sandbox and the reserved TEST-NET address; no public host is contacted.
- **M7:** clean-machine runs, race and crash matrices, and coverage (branch coverage is still below 80%).
