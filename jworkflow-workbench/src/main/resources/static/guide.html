JWorkflow Workbench guide

Version 0.1.0 · works offline

Start · Quickstart · Commands · Assistant · Build and test · Files · Recovery · Wiring your code · Limits

Workbench helps you create one JWorkflow workflow in an existing Java project. You draw the workflow with blocks. Workbench validates it, generates the Groovy definition and Java listener/command sources, and shows every source change for your approval before writing it. Your own services stay yours: Workbench never wires them for you.

Start

  • You need:
    • JDK 21 or later
    • Chrome or Edge
    • Windows 10/11 x64 or macOS on Apple Silicon
    • a single-module Maven or Gradle project targeting Java 17 or later, using org.jworkflow:jworkflow-core:0.1.0-SNAPSHOT
    Node and a database are not needed.
  • Run java -jar jworkflow-workbench-0.1.0.jar, optionally followed by your project folder (for example java -jar jworkflow-workbench-0.1.0.jar . from inside it). Your default browser opens.
    • The project folder is only a suggestion; nothing is read until you confirm it.
    • Workbench listens only on 127.0.0.1 and uses a one-time link; the tab that opens it owns the session. Closing that tab or typing /exit stops Workbench.
    • If the browser does not open, run Workbench in a terminal; it prints a one-time local address instead (--workbench.browser.enabled=false does this on purpose).
  • Windows paths: the java launcher cannot pass characters outside your system code page (for example 漢字) as arguments. If the JAR or project path contains them, start Workbench from inside that folder with relative paths.

Quickstart (about ten minutes)

  1. Confirm the project. Enter the project folder and choose Confirm project. Workbench shows the build system, Java target, core version and the commands, events and listeners it found in src/main/java.
  2. Confirm packages and output. Check the Java package for generated classes and the workflow folder (default src/main/resources/workflows), then choose Confirm packages and output.
  3. Name it. Enter a workflow name and version; the engine ID follows the name. Optionally review the .gitignore change for .jworkflow/.
  4. Build the flow with Add block (keyboard) or by dragging from the palette:
    • Start names the first node.
    • A step runs a command and names its success and failure targets.
    • A branch compares a workflow variable.
    • An end completes the workflow.
    The inspector edits every field, and the Blocks list selects any block.
  5. Save whenever you like; incomplete drafts are fine. Nothing is saved automatically.
  6. Generate saves, validates the saved draft and shows the Groovy preview. Errors block generation and warnings do not. Select a problem to jump to its field. A step may name a command that does not exist yet; Workbench will propose creating it.
  7. Review source changes. Choose Review source changes to see every file and its full diff, then approve or reject the whole set. Nothing is written before approval.
  8. Wire it up. Read the Integration plan (also saved as .jworkflow/integration-plan.md) and add the wiring it shows to your application.

Terminal commands

Commands must match exactly. Any other text is sent to the assistant.

  • /help: lists the commands.
  • /core: shows the supported core version.
  • /clear: deletes the current conversation and starts a new one. It is refused while an AI request runs.
  • /build: proposes a confined, offline build without tests.
  • /test: proposes the full configured test suite, confined and offline.
  • /cancel:
    • During an AI request, it stops the request and deletes that conversation.
    • During a build or test, it stops every process it started.
    • Otherwise it reports that nothing is running.
  • /exit: offers to save unsaved changes, stops running builds, then shuts down.
  • Ctrl+C: copies the terminal selection; it never cancels.

Only one operation runs at a time (an AI request, a build or a test). Other requests are refused, never queued.

Assistant

  • Availability: works only when OPENAI_API_KEY is set in the environment that starts Workbench. The key is read when a request is sent and never stored or shown. Without it, everything else works.
  • Model and data: requests go to the OpenAI Responses API, model gpt-6-astra, with store=false. Retention otherwise follows your OpenAI account terms. A request contains:
    • your message
    • this conversation's earlier messages
    • only what you share in the Assistant panel for this session: the current workflow and command names, and files you tick
    Secret-looking, ignored, binary and build files are never offered. Sharing ends when Workbench stops or the project changes, and is not restored when you resume a conversation.
  • What it can do: answer, and propose block edits. You see a preview and approve or reject the whole proposal; an approved proposal is one change that Undo reverts. It cannot read files, run commands or write sources. Source changes always go through Generate and the reviewed diff.
  • Conversations are saved in .jworkflow/conversations/ until you delete them. Requests stop after 10 minutes; a partial reply is kept and marked incomplete.

Build and test

  • Confinement first: /build and /test run only inside an operating-system sandbox. Before the first run, use Run confinement self-test in the Build and test panel. It proves on your machine, for this project, that the sandboxed build:
    • cannot read or write outside the project
    • cannot change your caches or reach the network
    • cannot keep processes running after it ends
  • Windows: the sandbox is an AppContainer. Workbench asks before giving it access to your project folder. It never changes other folders; if the self-test reports a tool or cache folder as unreadable, it prints the exact icacls command for you to run, for example for your Maven installation and %USERPROFILE%\.m2\repository. In this version, /build and /test support Maven projects only on Windows; build Gradle projects yourself.
  • macOS: the sandbox is sandbox-exec. It is enabled only after its self-test passes on your Mac.
  • Offline, read-only caches: builds run offline and never download. Your Maven or Gradle caches are read-only; anything new goes to .jworkflow/. If a dependency is missing, run your build once yourself (outside Workbench, with network access), then retry.
  • Approval every time: every run shows the exact command, folders, environment and 10-minute limit, and runs only after you approve it.
  • Output: streams to the terminal and is not saved. The integration plan records only the outcome and whether it still matches your current sources. Source apply and revert wait until a build or test finishes.

Files Workbench writes

Everything is inside your project's .jworkflow/ folder except the approved source changes and the path of the last project (kept in your user settings):

  • workflow.jworkflow.json: the workflow
  • integration-plan.md: the integration plan
  • applied.json: what Workbench last wrote
  • backup/: the latest revert point
  • conversations/: saved conversations
  • verification.json: the last build/test outcome
  • m2/, gradle-home/, tmp/: sandboxed build data

Recovery and undo

  • Interrupted writes: source changes are written all-or-nothing. If Workbench stops while writing, the next time you confirm the project it restores every file. If you edited one of those files meanwhile, it keeps the journal and tells you which file to check.
  • Revert: Review revert of last applied change undoes the latest applied set after you approve its reverse diff. It is refused if you have edited those files since.
  • Your own code is protected: Workbench never changes Java you wrote. A generated listener is updated only while you have not edited it, and a Groovy file you edited is replaced only after you confirm.
  • Undo covers editor changes in this session only; it never touches files or conversations.

Wiring your code

  • Per step action: each step action gets a listener (<Command>Listener, a StepHandler) that builds the command from the step's data and passes it to a service method you supply. Missing commands are created as records you can extend. Register them as the integration plan shows:
WorkflowEngine engine = WorkflowEngine.builder()
        .definitions(new ClasspathWorkflowDefinitionSource(List.of("workflows/order-flow.groovy")))
        .stepHandler("ChargeCard", new ChargeCardListener(payments::charge))
        .build();
  • Running steps: a step runs when its workflow instance receives an event or signal, not when the instance is created, and each step in a sequence needs its own signal. Start instances with engine.start(...) and deliver the events that drive each step.
  • Renames: if you rename the workflow, the old Groovy file and old engine ID are listed for you to clean up; Workbench never deletes them.

Limits in this version

  • One workflow per project.
  • Blocks: start, step, two-way branch and end, up to 500 blocks. Generate takes a few seconds at that size, mostly core compilation.
  • Workbench never generates Spring annotations, services, dispatchers or build changes.
  • No import, export or Save As.
  • On Windows, /build and /test support Maven only.
